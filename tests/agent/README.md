# Johar agent validation workspace

Temporary workspace for automated end-to-end validation of the installed Johar Android app.

The original 200-command inventory remains frozen in `docs/johar-200-command-validation.md` and `tests/agent/assets/johar-200-commands.tsv` for historical comparison.

The new baseline is a deterministic 1000-case evaluation matrix generated by:

```bash
python3 tests/agent/generate_1000_cases.py
```

That creates `tests/agent/assets/johar-1000-cases.tsv`. IDs `1..200` are preserved exactly from the original matrix. IDs `201..1000` must not be reshuffled after the first baseline run; future cases should use IDs above `1000`.

## Coverage

The 1000 cases are intentionally distributed by capability rather than created as random paraphrases:

- KNOWLEDGE: 100
- PLACE: 100
- NEARBY: 100
- UTILITY: 100
- ROUTE: 150
- COMPARISON: 80
- ITINERARY: 100
- LIVE_GUARDRAIL: 100
- TYPO_AMBIGUITY: 80
- NEGATIVE: 60
- STATEFUL: 30

Each TSV row carries six fields:

`id -> family -> query/turns -> allowed result types -> behavior contract -> state group`

For stateful cases, `|||` separates turns that must run in the same fresh `JoharActivity`.

## One-command baseline

Connect one Android device/emulator, then run:

```bash
bash tests/agent/run.sh
```

The script:

1. regenerates and validates the deterministic 1000-case matrix;
2. expands and clears logcat;
3. runs only `Johar1000CommandUiTest` through the real installed app;
4. drives Compose UI semantics instead of calling the router directly;
5. emits one structured `JoharAgent` JSON log row per case;
6. exports exactly 1000 rows to `tests/agent/results.jsonl`;
7. fails explicitly if fewer or more than 1000 rows are captured;
8. prints the status summary.

The expected runtime is much longer than the legacy 200-case run. The 200-case suite took roughly 11 minutes on the existing emulator, so budget approximately an hour for the first full baseline.

Runtime flow:

`case -> fresh JoharActivity -> each turn -> johar_chat_input -> send -> wait for answer count to increase and thinking to disappear -> inspect final johar_latest_answer + result tag -> classify -> emit JSON log row -> host exports results.jsonl`

All non-stateful cases start from a fresh activity. Stateful cases keep their own turns together in one activity but do not share state with other cases.

## Behavior contracts

Automated classification is triage, not the final product verdict. The matrix records the expected behavior so post-run analysis can separate:

- `PASS`
- `DATA_GAP`
- `PARSER_GAP`
- `UI_GAP`
- `SAFETY_GROUNDING_FAIL`
- `CRASH_ANR`
- `HARNESS_ERROR`

Important principles:

- missing offline data is not automatically a parser defect;
- live/current claims must stay unconfirmed unless a live source is actually wired;
- negative/adversarial cases must not invent places, routes, prices, ratings, safety, availability, or guarantees;
- typo tests may resolve or conservatively clarify, but must not make unsafe guesses;
- itinerary order should remain the requested order unless a real optimizer exists;
- comparison must not invent an unsupported qualitative winner.

## Result file

`tests/agent/results.jsonl` is scratch output. One JSON object represents one evaluation case and includes:

- id
- original query or stateful turn sequence
- detected final result type
- visible final response text
- automated classification
- elapsed milliseconds
- expected family / contract / allowed types

Freeze the first complete 1000-row run as **Baseline V1** before changing production behavior. Analyze failures by category, change one failure family at a time, and re-run the same stable IDs to measure regression and improvement.
