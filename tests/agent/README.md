# Johar agent validation workspace

Temporary workspace for automated end-to-end validation of the installed Johar Android app.

The original 200-command inventory remains frozen in `docs/johar-200-command-validation.md` and `tests/agent/assets/johar-200-commands.tsv`. The deterministic 1000-case baseline is generated by `python3 tests/agent/generate_1000_cases.py`; IDs `1..1000` must stay stable after Baseline V1.

## One-command baseline

From repository root with one connected Android device/emulator:

```bash
bash tests/agent/run.sh
```

The host runner executes the 1000 cases in 50-case process shards. At the beginning of each shard, the app process is restarted. Inside that shard, `JoharActivity` is launched once and remains warm for all 50 cases.

For independent cases, the harness resets only conversation/session state before the next case:

`same Activity -> clear messages/map targets/router clarification state -> next query`

This deliberately keeps expensive app-level objects warm, including the database/repositories, spatial lookup, routing data and Compose Activity setup. It avoids paying Activity/splash/bootstrap cost for every query and also prevents unrelated previous chat state from contaminating the next independent case.

Stateful cases still keep all turns in the same conversation. The reset happens before the stateful scenario, not between its turns.

At the end of each 50-case shard, the process is force-stopped before the next shard. This bounds long-run heap/native accumulation while preserving the speed benefit of a warm Activity.

## Runtime flow

Independent case:

`process shard -> one JoharActivity -> reset conversation -> input -> send -> wait -> inspect latest answer -> classify -> emit JSON row -> reset conversation -> next case`

Stateful case:

`reset conversation -> turn 1 -> wait -> turn 2 -> ... -> inspect final answer -> classify -> emit one JSON row`

The latest-answer subtree is used for result-type detection, so earlier turns in a stateful scenario do not incorrectly determine the final result type.

## Reset boundary

`resetConversationForTesting()` is an evaluation hook only. It clears:

- rendered/user/Johar messages back to the welcome message;
- map action targets;
- router pending clarification/category state.

It does **not** recreate repositories, Room, routing graph, offline data, or the Activity. Production query behavior is unchanged.

## Result capture

Every case emits one structured `JoharAgent` JSON log row. `tests/agent/run.sh` verifies exactly 50 rows per shard and exactly 1000 rows overall before accepting the baseline. Final output is written to:

`tests/agent/results.jsonl`

Each row includes ID, query/turn sequence, detected final result type, visible response, classification, elapsed milliseconds and the expected behavior contract.

Automated classifications are triage, not the final product verdict. Review non-pass and suspicious PASS cases before product changes. Freeze the first complete 1000-row run as **Baseline V1**.
